# Log-Analysis-Tool
A SIEM-style log analyser.

# Overview
For my next project, I decided to make a log analyser to improve my Cyber Security skills. This project will take inputs:
- Apache logs
- SSH logs
- Windows event logs
- Firewall logs

...and do the following:
- Detect failed logins
- Detect brute force attacks
- Detect suspicious IPs
- Generate a timeline
- Generate a HTML report
- Visualise attacks with graphs

# Planning
1. Choose an architechture. Python would be the most logical language to use for this project. I will also need to create an appropriete file layout that can hold logs, parsers, detection, timelines, reports etc.
2. Normalise logs. Logs need to look similar regardless of the type of log they are to make programming in the backend easier.
3. Build parsers. Parsers will be used to take the logs from each type and normalise them into the same log regardless of type. We can use a parser to extract what's important from logs, such as timestamps, IP addresses, usernames, error codes etc.
4. Build a detection engine. This will be the hardest part of the program to write. To simplify this, I will add each detection as a rule. For example, rules could be failed logins, brute force attacks, suspicious IPs, port scanning (see github profile) and multiple attack sources.
5. Failed login event. This is the easiest detection to create, as it can be made using just an if statement. If detection is succesful, we can gather useful stats for the report, such as IP addesses, number of failures, and time.
6. Brute force attacks. A brute force attack will look like a bunch of failed logins from the same IP address within the same time window in the logs. The rule could be 5 failed logins, same address and within the same 5 minutes.
7. Catogorising suspicious IPs. We need to use an algorithm to calculate if an IP address is suspicious. We can give addresses points each time a suspicious thing happens, and then if an address reaches n points, we can label it suspicous. A failed login could be one point (5 is 5), open port could be 5, firewall deny could be 1, and a web attack pattern could be 3. This is where the SIEM style scoring will be used. 1-3 points is not suspicious, 4-6 is meduim risk and 7+ is high risk (blocked).
8. Timeline. The timeline is created by sorting all the events by timestamp and saving them to a log (txt).
9. HTML report. For this, there are templates that can be used, but from my research, Jinja2 appears to be the best for creating HTML reports. The report can outline the analysis period, which a user will create at the start of the program, the top few suspicious IPs, attacks timeline and maybe more.
10. Visualisation (stretch). This could be useful to add as another extract. Graphs could show the number of attacks or suspicous events over the analysis window, bar charts could show the types of events and IP addresses.

# Organising
First I added the file layout that will be used in this project to create a simple and efficient architechture:
- The data files (apache, firewall, SSH and windows) will contain logs from their respective sources.
- The reports file, which is empty for now, will contain reports generated by the program.
- The src file contains 4 parsers (one for each of the types of logs entering the program), 3 detection engines (each type of suspicious event), the analyser itself, main program entry, reports generator and timeline generator.
- The templates file contains the template for the output log.

# Normalising
Next I need to create a normalised log, so that my detection engines won't need to understand all the different types of logs and can instead read from a normalised log which the parsers have converted inputs into. I decided my global logs will be structures as follows (example values):

timestamp: 2026-08-12 15:03:00

source: apache

event_type: HTTP request

ip: 192.168.1.50

status: 404

message: anything

username: root

event_id: 1234

# Parsing
Next I built parsers in the files outlined in the file parsers under src. The parsers would parse inputted logs into the global log I designed above. The apache parser parses access logs by extracting IP, HTTP method, status code, path, referrer, user agent and username. It also parses error logs, and normalizes into the format outlined above. The parsers are designed to be used by my detection engines and report generator. I also build similar windows, ssh and firewall log parsers.

# Detecting
Next I built the detection engine. It can take log inputs which have been parsed into the standardised format, check for the rules I highlighted in the plan and output alerts. The rules we check for are:
- A failed login
- Brute force attack
- Suspicous IP addresses
- Open ports
- Multiple attack sources

We are able to output alerts, which can contain the type of alert, address, target etc.

# Logging in
Next I created the first detection engine, which will detect for failed login attampts using the standarised logs we parsed. The detector finds where event_type is failed login or failed logon or where status is failed or invalid user. It returns a list of alerts in the format outlined.

Note that for each detection engine, a pycache file was created to allow it to work throughout the program.

# Brute forcing
A brute force attack is defined as 5 or more failed logins within 300 seconds from the same IP address. Next, I created the detection engine for this rule. This detection engine is easier to create, because it can look at the alerts generated by the logging in detection engine and alert when the rule is met, so essentially it is a simple conditional.

# Suspicious IP detecting
This detection engine is simply going to score the IP addresses we see into three catigories; no risk, caution risk and critical risk. It will categorise each suspicious alert by giving it a score:
- A failed login will be 1 point
- 5 failed logins (brute force attack) will be 5 points
- An open port scan will be 5 points
- A firewall deny will be 1 point
- A web attack pattern will be 3 points

And then, for each IP address:
- 0-2 points will be no risk
- 3-6 points will be caution risk
- 7+ points will be critical risk

This is an example of a real world risk scoring SIEM-style system. 

The final detection engine also includes a detect method returning suspicous IP alerts and a detect_summary method returning grouped risk counts.

# Timelining
Next I need to look through all the logs and categorise them by timestamp in order to create a timeline of all the alerts seen in the detection window. The timelining is seen in the file timeline.py:
- Can add multiple alerts to the timeline
- Can get all the events in chronological order
- Format into a human readable text format
- Save the formatted timeline to a txt file
- Group events by severity (No, Caution, Critical)
- Group events by type (failed login, firewall failure etc.)
- Group events by log source (IP)
- Get statistics such as the total events, events per severity or type etc.
- Add a single alert to the timeline
- Reset the timeline

The methods are all ready for integration.
